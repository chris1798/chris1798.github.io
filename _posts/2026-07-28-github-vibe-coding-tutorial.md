如果你每天被這些名詞轟炸，卻還是搞不懂他們到底在幹嘛，這支影片用最白話的方式，搭配實際案例，帶你一次搞懂 Git 和 GitHub 的概念與用法。看完你就聽得懂 AI 在說什麼，用 AI 開發更踏實。

## 1. 為什麼需要 Git？（0:00）

假設你今天心血來潮，用 Cursor 請 AI 幫忙做了一個記帳軟體，過沒多久 AI 就順利幫你把第一版的畫面給做出來了。

但這個時候，你遇到了一個問題：**寫好的程式到底可以放在哪裡呢？**

- 你不想讓程式只能留在這台電腦裡
- 之後可能想換別台電腦接著寫
- 或者想把做好的東西分享給朋友看

這時候，你就會用到第一個關鍵工具——**GitHub**。

但下一個問題就來了：**怎麼把電腦裡的資料夾上傳到 GitHub？**

其實你不能像用 Google Drive 那樣，直接把資料夾拖進去就好。因為 GitHub 主要是用來讓大家協作跟追蹤程式碼進度的，所以它**不收單純的檔案，只接收已經做好版本紀錄的專案**。

> 💡 **沒有 Git 的困擾**：如果 AI 不小心把原本好好的程式給改壞了，你根本不知道 AI 剛剛到底動了哪些檔案，也完全不知道該怎麼讓程式恢復到上一個正常的狀態。但有了 Git 就不一樣了，**不管 AI 怎麼亂改，你隨時都有辦法把程式恢復到之前正常的樣子**。

## 2. GitHub 和 Git 的差別（1:02）

先把這兩個東西分清楚：

| 工具 | 角色 | 比喻 |
|------|------|------|
| **GitHub** | 在雲端儲存和管理程式碼的網站 | 程式碼的雲端硬碟 |
| **Git** | 在本機端管理程式碼版本的工具 | 程式碼的版本記錄簿 |

- 工程師們都會把程式碼上傳到 GitHub，讓有權限的人都能夠隨時查看，甚至是一起編輯
- 在上傳之前，必須先在自己的電腦裡，幫程式碼建立起版本紀錄系統
- 這個建立版本紀錄的關鍵工具就是 **Git**

## 3. Commit 與 Push（3:21）

### Commit = 遊戲存檔

當你有這種想要存檔的念頭時，對應著 Git 裡面的 **Commit** 功能。

你可以把 **Commit 想像成程式在玩遊戲的時候，打大魔王之前會先手動存檔的那個動作**。

**Commit 最大的價值**：
- 幫程式碼建立了一個**絕對安全的檢查點**
- 只要你做個 Commit，這份正常的狀態就被**永久封存**了
- 就算 AI 發瘋，把你的程式碼全刪了或改成亂七八糟，你都可以**瞬間還原**回 Commit 那個完美狀態

> ⚠️ **重要觀念**：Commit 不是上傳，也不是把東西放到 GitHub 上。Commit 只是單純在你自己的電腦裡面，幫目前的狀態留下一份紀錄而已。

當 AI 寫完一段程式主動問你要不要 Commit 的時候，其實就是在問你：「現在這個好好的狀態，你要不要先幫他存個檔、買個保險？」

### Push = 上傳到雲端

當你有想把電腦裡存好的進度上傳到雲端的念頭時，對應的 Git 動作就叫做 **Push**。

**Commit 跟 Push 完全是兩回事**：
- **Commit** = 在本地電腦裡存檔
- **Push** = 把本地存檔推送到雲端的 GitHub

### 第一次 Push 的指令

第一次做 Push 的時候，AI 可能會跑出一長串指令，像是設定 Remote 或是 Push 到 Origin Main。這些其實很好理解：

| 名詞 | 意思 |
|------|------|
| **Remote** | 遠端的例子（相對於 Local 本地） |
| **Origin** | 你在 GitHub 上的專案資料夾 |
| **Main** | 這個專案目前的官方正式版 |

所以 **Push 到 Origin Main** 翻譯成白話文就是：「請幫我把我寫好的正式版本傳送到雲端。」

### ⚠️ 重要提醒：用 .gitignore 排除機密檔案

在你的記帳軟體裡，可能藏了一把用來串接金流的 **API 金鑰**（你可以把金鑰想像程式你家大門的鑰匙）。

如果金鑰跟著程式碼一起被 Push 到 GitHub 上，就等於把鑰匙公開貼在網路上，任何人都可以用，甚至拿去倒刷你的信用卡帳號。

> 前面提到的情況，就算 AI 把程式改壞了都還有救，但金鑰一旦外洩流傳出去，那就真的救不回來了，只能整把作廢重新申請。

所以在 Push 之前，我們會需要用到一個叫做 **`.gitignore`** 的檔案，作用是告訴 Git 這些特定的檔案**不要追蹤、絕對不要上傳**。

> 💡 **懶人提示**：不用自己去記哪些檔案該檔，直接跟 AI 說：「幫我確認 .env 檔、密碼、還有各種金鑰機密檔案都已經放進 .gitignore 裡面，絕對不要 Commit 上去。」

## 4. Clone、Pull 與 Branch（6:11）

### Clone = 複製遠端專案到本地

當你的朋友在 GitHub 上分享了一個專案連結，你想把這個專案抓到你自己的電腦裡，這個動作叫做 **Clone**。

> ⚠️ **注意**：Clone 跟你在 GitHub 網頁上看到的「下載」是完全不一樣的東西！
> - 用「下載」抓下來的只是一包純粹的檔案，裡面**沒有被 Git 追蹤的記錄**，之後沒辦法同步
> - 用 Clone 抓下來的等於**正式加入這個專案**，之後做修改想要上傳回去都會很輕鬆

### Pull = 同步最新版本

當你的朋友在 GitHub 上更新了程式碼，你想把最新改好的版本抓回你的電腦，這個動作叫做 **Pull**。

### 合作基礎循環

| 動作 | 時機 | 指令 |
|------|------|------|
| 第一次加入專案 | 把程式碼抓下來 | `Clone` |
| 平常同步別人的最新進度 | 拉取最新程式碼 | `Pull` |
| 自己改好東西想存檔 | 本地存檔 | `Commit` |
| 想把自己的進度送上雲端 | 上傳到 GitHub | `Push` |

## 5. Branch = 平行開發（分支）

當你要開發一個新功能（例如幫記帳軟體加上資料庫功能），你**不想要直接在目前穩定的 Main 分支上開發**，因為你怕把自己辛苦的東西改壞了。

這時候就要用到 **Branch（分支）**。

### 為什麼要用 Branch？

- 當 AI 幫你寫比較複雜的大功能時，通常不會一次就寫對，需要反覆試錯修改好幾次
- 如果你一直都在 Main 上面改，在 AI 試錯的這段期間，你的程式就會一直處於**半壞掉的狀態**
- 這時候如果朋友想看看你的軟體，或者發現拼字錯誤需要緊急修正，就會非常尷尬

> 💡 **神奇辦公桌比喻**：把你的專案資料夾想像成一張神奇辦公桌，Branch 就像桌子邊上的平行時空切換按鈕。當你按下 Main，桌上呈現穩定版本的程式碼；當你按下新功能 Branch，桌上的東西會瞬間變成你正在開發中的草稿。

**最壞的狀況**：如果新功能的草稿真的被 AI 改爛了，直接把那個 Branch 刪掉然後切回 Main，你的 Main 依然毫無傷。

> 💡 **Vibe Coder 提示**：你不用記住所有指令，只要跟 AI 說：「先幫我從 Main 開條新的 Branch 專門用來做資料庫功能，之後所有的改動都幫我 Commit 在這條 Branch 上，絕對不要動到 Main。」

## 6. Worktree = 同時讓多個 AI 平行開發（10:42）

### 為什麼需要 Worktree？

當你要開發資料庫的同時，又想要讓另一個 AI 幫你重新設計 UI 畫面。

但如果你直接叫 AI 同時在同一個資料夾裡做這兩件事，絕對會是一場災難。

**Branch 的瓶頸**：Branch 的意義在於可以切換不同時空，但**同一時間你只能看見一個畫面**。如果叫兩個 AI 同時在同一張桌子上做事，他們會為了搶桌子的顯示狀態而大打出手。

### Worktree 的解決方式

Worktree 就像直接去 IKEA 買第二張實體的辦公桌放在旁邊。

| 比較 | Branch | Worktree |
|------|--------|----------|
| 比喻 | 同一張桌子上切換時空 | 兩張實體的桌子 |
| 同一時間 | 只能顯示一個分支 | 可以同時顯示多個分支 |
| 資料夾 | 共用同一個 | 各自獨立的實體資料夾 |
| 優點 | 簡單、節省空間 | 讓多個 AI 平行開發不互相干擾 |

> 💡 **Vibe Coder 必學**：以前的工程師不太會用到 Worktree，因為一個人沒有三頭六臂。但現在身為 Vibe Coder，你很可能會同時開兩三個 AI Agent 讓他們平行工作，這時候就一定會需要用到 Worktree。

## 7. PR（Pull Request）與 Merge 合併（10:42）

### PR = 改動提案

當你把 Branch 上的功能開發完成後，在正式合併回 Main 之前，你需要先讓朋友 **Review（審查）** 一下。這個動作在 GitHub 上叫做 **PR（Pull Request，拉取請求）**。

你可以把 PR 想像成是一份**改動提案**：
- 開好 PR 之後，這份提案會被送到 GitHub 上
- 讓大家來審查這次改動合不合理
- 你也可以直接請 AI 幫忙整理：「幫我把這條 Branch 開一個 PR，內容說明這次做了什麼功能、改了哪些檔案、還有要怎麼測試它」

### Merge = 正式合併

當大家都檢查過你的改動沒有問題之後，最後一個動作就是將程式碼變動**正式合併回 Main 裡面**。

這個合併的動作對應的 Git 指令就叫做 **Merge**。

> ⚠️ **新手最容易誤會的地方**：因為這個合併是在 GitHub 網頁上發生的，所以你自己電腦本機的 Merge 並不會自動同步跟這邊。

## 8. 改壞怎麼救（15:53）

### 情況一：Merge 時遇到 Conflict 衝突

當兩個分支的程式碼改到了同一行，Git 會跳出 Conflict 警告。

> 💡 **不要慌！Conflict 不是世界末日**，這只是在等你下達明確的決策。AI 通常會用三種方式幫你和稀泥：
> 1. **二選一**：保留其中一邊（如果其中一邊是正確的）
> 2. **兩邊都留**：當兩邊不衝突但 Git 判定衝突時
> 3. **AI 分析後自動選擇**：AI 看到標記後分析兩個版本各自想幹嘛，再決定

### 情況二：Commit 之後想撤銷

如果你不小心 Commit 了錯誤的版本，可以用 **Revert** 安全地把錯誤給撤掉。

### 情況三：程式被 AI 改壞到無法玩

只要**還沒 Commit**，就可以用 **Restore** 一件復原。

## 完整術語對照表

| 術語 | 白話翻譯 | 使用時機 |
|------|----------|----------|
| **Git** | 本機版本管理工具 | 需要管理程式碼歷史時 |
| **GitHub** | 雲端程式碼儲存網站 | 需要備份或協作時 |
| **Commit** | 存檔 | 完成一個功能想要留底時 |
| **Push** | 上傳雲端 | 把本地存檔同步到 GitHub 時 |
| **Pull** | 拉取同步 | 同步別人的最新程式碼時 |
| **Clone** | 複製專案 | 第一次加入專案把程式碼抓下來時 |
| **Branch** | 分支 | 開發新功能不影響主線時 |
| **Worktree** | 多工作區 | 同時讓多個 AI 平行開發時 |
| **PR (Pull Request)** | 改動提案 | 合併前請人審查時 |
| **Merge** | 合併 | 審查通過後把新功能合併回主線時 |
| **Revert** | 撤銷 | 不小心 Commit 了錯誤版本時 |
| **Conflict** | 衝突 | 兩個分支改到同一行程式碼時 |

## 總結

或許對你來說，Git 是一堆難記的英文單字，但你只要有能力**指揮**就可以了。

當 Claude 或 Cursor 問你要不要 Commit、要不要開 Branch、要不要發 PR 的時候，他其實是在問你：
- 要不要先**存檔**？
- 要不要開個空間來**隔離風險**？
- 要不要把寫好的東西**交出去給別人檢查**？

只要這些判斷你聽得懂，你用 AI 開發就會踏實很多。
